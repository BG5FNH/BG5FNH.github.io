第 01 章　一次访问的全过程（从按下回车到看见页面）

DNS、TCP、TLS、HTTP、Nginx、PHP 各干一件事。这一章把这条链拆开，并标出每一步能被怎么利用。

本章你会得到

  • 能按顺序说出一次访问经过的 8 个环节，以及每个环节"在解决什么问题"
  • 看懂一条原始 HTTP 报文：哪部分是头、哪部分是体、哪部分用户可以随便改
  • 知道每个环节对应什么攻击（后面章节的目录）

第 1 步：DNS —— 把"名字"换成"门牌号"

计算机之间通信靠 IP 地址（比如 104.21.3.5），但人记不住数字，于是有了域名。 DNS 就是那本电话簿：给名字，还你号码。

为什么需要它 / 它解决了什么

没有 DNS 时，换服务器就要通知所有人改 IP；有了 DNS，你只改自己那条记录， 全世界还是访问同一个域名。它简化的是"迁移成本"。

代价是：你访问谁，由这本电话簿决定。所以它天然是攻击目标：

  • 改本机 hosts 文件（本地电话簿）→ 把域名指向攻击者；
  • DNS 劫持 / 缓存投毒 → 改的是路上那本；
  • 反过来，攻击者也能用 DNS 做"外带通道"：把偷到的数据塞进子域名发出去（DNSLog）。
nslookup shop.example.com        # Windows / Linux 都有
dig shop.example.com A           # Linux 常用，看 A 记录
ping shop.example.com            # 顺手看解析到哪个 IP

第 2 步：TCP —— 先确认"双方都能收发"

IP 只负责"尽力送到"，不保证对方在听。TCP 在它上面加了一层： 先握手确认通路，再按顺序、可重传地传数据。

为什么需要它

网页内容不能缺一块（少一行 JS 就白屏），所以需要"可靠"。三次握手就是在问： "我发的你能收到吗？你发的我能收到吗？我们同步一个起始序号吧。"

安全视角：端口是 TCP 上的门牌号。服务器开了哪些端口，就等于告诉你能从哪些门进去。 扫端口就是在数门（第 10 章）。

curl -v http://example.com      # -v 会打印 TCP 连接、请求头、响应头
netstat -ano | findstr :80      # Windows：谁占着 80
ss -lntp                        # Linux：监听中的 TCP 端口

第 3 步：TLS —— 让中间人看不懂

HTTP 是明文：路上的路由器、代理、Wi-Fi 都能看见你发了什么。 TLS 在 TCP 之上再套一层加密，并用证书证明"对面确实是这个域名"。

为什么需要它

没有 TLS，登录密码在咖啡厅 Wi-Fi 上就是明文。TLS 解决两件事： 保密（别人看不懂）和身份（对面不是假冒的）。

安全视角：如果攻击者拿到了 TLS 的会话密钥（比如抓包里带了 SSLKEYLOGFILE）， 加密就形同虚设 —— 这正是"HTTPS 流量分析"类题的入口（第 11 章会用它解 web4.zip 那种题）。

一个常见误解

"用了 HTTPS 就安全"是错的。HTTPS 只保证传输过程不被偷看， 不保证服务器代码没有 SQL 注入。锁头保护的是信封，不是信的内容是否合法。

第 4 步：HTTP —— 一句"请求"，一句"响应"

HTTP 的设计哲学是"简单到能用手写"：一行请求行、若干头、一个空行、然后是体。 它的每一次请求都是独立的（无状态）—— 服务器不会记得上一次是你。

为什么要设计成"无状态"

因为早期网页只是"读文档"，服务器要同时服务成千上万人，记住每个人太贵。 无状态让它简单、可水平扩展。

代价：需要登录的网站必须每次自带凭证（Cookie / Token）。 这个"每次都要带、且由客户端保管"的设计，就是认证类漏洞的根源（第 7 章）。

第 5~6 步：Nginx 与应用服务器 —— 谁来决定"这句请求交给谁"

真实网站通常不是一个程序干完所有事，而是分工：

角色它负责它不管
Nginx（前端）监听 80/443、按域名/路径分发、发静态文件、限流、TLS 终止不执行业务代码
PHP-FPM / Tomcat / Gunicorn（应用服务器）跑代码、连数据库、生成 HTML不直接面对公网
数据库存数据、按 SQL 取数据不知道"用户是谁"
为什么要拆成两层

因为两件事的"瓶颈"不同：Nginx 擅长同时接一万个连接（事件驱动）， PHP 擅长执行业务逻辑但每个请求要占一个进程。拆开后各自扩展，还能让应用服务器不暴露在公网。

安全视角："这个路径交给谁"这条规则，本身就是攻击面。 路径解析差异（/a.php/x）、后缀匹配（.php.jpg）、 上游信任（请求走私）全在这一层（第 3 章）。

第 7 步：应用代码 —— 用户输入变成页面的地方

应用拿到请求后通常会做四件事，这就是后面所有漏洞的舞台：

  1. 认人：看 Cookie / Token / 参数里的身份；
  2. 取数：把参数拼进 SQL、拼进文件路径、拼进命令；
  3. 判断：密码对不对、余额够不够、有没有权限；
  4. 输出：拼 HTML、返回 JSON、跳转。
唯一的判据：数据有没有"越界"

用户给的一切都只是字符串。危险发生在程序把这段字符串当成了别的东西： 当成 SQL 语法、当成文件路径、当成命令、当成模板代码、当成身份。 这一条会贯穿第 5~9 章。

第 8 步：响应 —— 攻击者也在读它

响应不只有 HTML，还有头：

响应头 / 字段它想说什么攻击者拿它干什么
Server: nginx/1.20.1我是谁、什么版本查这个版本的已知漏洞
Set-Cookie: PHPSESSID=…这是你的身份票据偷 / 猜 / 伪造
Location: /login去这儿看逻辑、找跳转绕过
报错页（堆栈/路径）我出错了，原因是…泄露绝对路径、框架版本、SQL 语句
在工具箱里看这一步

「洪水」首探会把响应头、状态码、表单、可疑长串全抓下来，写在第一个节点里； 「发包工作台」可以手改任意头重发；「敏感文件探针」专门找报错页和备份文件。

本章小结（背这张表就够了）

环节解决的问题出问题会怎样
DNS名字→IP被指向假站 / 被当外带通道
TCP可靠传输端口暴露、被扫、被爆破
TLS保密 + 身份密钥泄露 = 明文
HTTP一问一答头/参数全可控；无状态要自带凭证
Nginx分发、静态、限流路径/后缀/Host 解析差异
应用业务逻辑输入被当成代码（第 5~9 章）
DB存与取注入、越权读
响应给结果信息泄露
