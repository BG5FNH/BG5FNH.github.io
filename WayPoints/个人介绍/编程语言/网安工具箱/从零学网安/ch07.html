第 07 章　认证与会话：我是谁，以及我怎么证明

密码怎么存、登录之后服务器怎么记得你、凭证为什么能被伪造 —— 这一类题占了入门的第二大块。

本章你会得到

  • 哈希 vs 加密的区别（决定你能不能用"解密"的思路）
  • Cookie / Session / JWT 三种凭证的强弱与攻击面
  • 四类认证绕过：弱口令、注入登录、令牌伪造、越权

密码为什么要"哈希"存，而不是加密存

加密（encrypt）哈希（hash）
能不能回推能（有密钥就能解开）不能（只能正向算）
用途传输、存储需要还原的数据只需要"核对是否一致"的东西（密码）
例子AES、RSAMD5、SHA-256、bcrypt
为什么密码必须单向

因为网站永远不需要知道你的密码原文，只需要判断"你这次输的"和"上次设置的"是不是同一个。 单向哈希能做到这点，而且数据库泄露时攻击者拿不到原文。

但哈希也不是万能的：弱口令可以被字典撞出来（彩虹表）。 所以现代做法是"加盐 + 慢哈希"（bcrypt/argon2），让每次计算都很贵。

Cookie vs Session vs JWT

CookieSessionJWT
存在哪浏览器服务器（只把 id 给浏览器）浏览器（自带签名）
服务器要不要存不用要（内存/Redis/文件）不用（无状态）
怎么能伪造直接改值（如果没签名）偷/猜 session id改 payload + 伪造签名
典型题role=admin 直接改session 固定、session 文件包含alg=none、弱密钥、kid 注入
看到 Cookie 先做三件事
  1. 改一个值，看页面反应（role=user → role=admin）
  2. 看它像不像 base64 / JSON / JWT（三段用 . 分隔就是 JWT）
  3. 看有没有 HttpOnly（有的话 JS 偷不到，但服务端仍然可能被骗）

四类认证问题

① 弱口令 / 默认口令

不是"漏洞"，是运维习惯。但比赛里常见：admin/admin、admin/123456、 test/test。工具里 login_cookie 就是先试弱口令再改 Cookie。

② 登录框 SQL 注入

// 代码
$sql = "SELECT * FROM users WHERE name='$u' AND pass='$p'";
// 输入 u=admin' -- -    p=任意
// 变成：SELECT ... WHERE name='admin' -- -' AND pass='...'
// 结果：只要知道用户名就能登录

③ 令牌伪造（JWT 三种典型）

问题怎么发现的怎么打
alg: none解出 header 看到算法把 alg 改 none，去掉签名段
弱密钥（HS256）签名是 HMAC，密钥可能是 secret用字典离线爆破密钥，再自签
kid 可控header 里有 kid 字段kid 路径穿越读文件 / kid 拼进 SQL 取密钥

④ 越权（IDOR）

登录了，但能看到别人的数据。典型：/api/user/1 改成 /api/user/2。 它属于"授权"问题，不是"认证"问题 —— 你确实是合法用户，只是不该看这条。

为什么越权特别常见

因为程序员通常只写"有没有登录"（认证），忘了写"这条数据是不是你的"（授权）。 而"换一个 id"是零成本攻击：不需要任何工具，改个数字就行。所以工具里专门有 id_scan。

验证码、二次验证为什么也常被绕过

实现方式破法本质
验证码明文写在页面/JS 里直接抄形同虚设
验证码校验后不销毁同一枚反复用状态没更新
不填就跳过校验省略字段判断写成 if code and code != want
二次验证（短信码）跳步 / 硬编码后门 / 不绑账号状态机缺一步
工具箱里对应什么

login_cookie（弱口令+Cookie 越权）、login_inject（登录框注入）、 jwt_forge/jwt_confuse/jwt_kid/jwt_jku（令牌伪造四件套）、 captcha_login（验证码）、otp_bypass（二次验证）、id_scan（越权遍历）。 「JWT / Token 分析」面板可以解出 header/payload、改完再签。

本章小结

要点一句话
哈希不可逆别想着"解密"密码，只能猜/撞
凭证由客户端保管就有风险Cookie 可改、JWT 可伪造、session id 可偷
认证 ≠ 授权登录成功不代表能看别人的数据
验证码看实现三种常见松法：明文、可复用、不填就过
