第 13 章　进阶：代理层、协议层与「看不见的」漏洞

前面十二章覆盖了 80% 的基础题。这一章补剩下的那 20%：Host 头、请求走私、缓存投毒、原型链、SAML、竞态与杂项。

本章你会得到

  • 六个"不靠注入"的漏洞类别，各自的判断信号
  • 知道它们为什么难：没有明显的 payload 回显，要靠间接证据
  • 一份"看到这个信号就该想到它"的对照表
先说实话

这一章的内容在省赛里出现频率远低于前十二章，但一旦出现，往往就是拉开差距的题。 建议：先能稳定做掉基础题，再回来读这一章。

① Host 头：一个"看起来只是域名"的输入

HTTP/1.1 必须带 Host，因为一个 IP 上可能挂很多站。服务器用它在内部路由。

为什么它能出事

因为代码里经常拿 Host 去拼绝对地址：密码重置链接、 跳转地址、静态资源前缀。而这些值会被写进邮件、写进缓存、写进数据库。 攻击者改一个 Host，就能让"发给用户的链接"指向自己的域名 —— 用户点开时 token 就送到攻击者手里。

# 判断：改 Host 后，页面里的绝对链接跟着变了吗
curl -H "Host: evil.example" http://TARGET/forgot
# 响应里出现 http://evil.example/reset?token=… → 有戏

# 常见变体：X-Forwarded-Host / X-Host / Forwarded
curl -H "X-Forwarded-Host: evil.example" http://TARGET/
现象说明怎么利用
页面绝对链接变了用了 Host 拼 URL重置密码/邀请链接拿到 token
访问任意 Host 都返回同一站没做 Host 校验（默认站点）缓存投毒 / 密码重置污染
403 但改 Host 就过按 Host 做访问控制绕过"只允许内网域名"

② 请求走私（HTTP Smuggling）：两个解析器意见不一致

链路是"前端代理 → 后端服务器"。如果两边对"请求体有多长"理解不同， 就会有一部分字节被后一个请求吃掉 —— 于是我们能"偷"一个请求。

POST / HTTP/1.1
Host: t
Content-Length: 6
Transfer-Encoding: chunked

0

G
为什么会有这种不一致

因为 HTTP 有两个表示"body 多长"的头：Content-Length（数字）和 Transfer-Encoding: chunked（分块）。规范说"两个都有时以 TE 为准并应拒绝"， 但很多实现各自处理：有的看 CL、有的看 TE、有的把两个都信。差异就是缝隙。

类型谁看 CL、谁看 TE结果
CL.TE前端看 CL，后端看 TE后端把剩下的当成下一个请求
TE.CL前端看 TE，后端看 CL同上前提反
TE.TE两边都看 TE，但一个被混淆头骗过用畸形头让一方忽略 TE
为什么这类题很难"看见"

因为你发的是一个请求，效果却作用在别人的下一个请求上。验证方式通常是 "发两发，看第二发的响应是不是第一发的" —— 需要精确控制连接复用。工具里是 smuggle 策略，靶子用两台真服务器模拟前后端。

③ 缓存投毒 / 缓存欺骗：缓存键比内容粗

CDN 为了加速，会把响应存起来。它判断"这份内容属于谁"用的是 缓存键（通常=路径）。

问题怎么发现后果
查询串不在缓存键里访问 /p?x=1 再访问 /p?x=2，内容一样把带攻击 payload 的页面缓存给所有人（XSS）
路径后缀被忽略/profile/x.css 返回 profile 内容缓存欺骗：别人能读到你的隐私页
Host/头参与不参与换头看缓存是否命中投毒到"看起来是静态文件"的路径
# 判断缓存：看响应头
curl -I http://TARGET/a.js
# X-Cache: HIT / MISS、Age、CF-Cache-Status 都是信号

# 投毒尝试：让缓存记住我们想要的响应
curl -H "X-Forwarded-Host: evil.example" http://TARGET/a.js
curl http://TARGET/a.js          # 第二次如果带上了 evil → 投毒成功

④ 原型链污染（JavaScript）

JS 的对象都有"原型"，查找属性时会沿原型链往上找。如果合并逻辑允许写 __proto__，你就能给所有对象加属性。

// 漏洞：深合并时没过滤 __proto__
merge(target, JSON.parse(userInput))
// 输入：{"__proto__": {"isAdmin": true}}
// 之后任何对象 obj.isAdmin 都是 true
为什么这很隐蔽

因为没有任何一个地方写着 isAdmin = true。它污染的是"默认值"， 只有在别的代码读这个属性时才生效（比如权限判断、模板渲染、child_process 的参数）。 所以判断方法是：找一个"接收 JSON 并合并"的接口，然后看权限/行为是否变化。

⑤ SAML / OAuth：断言与跳转的信任问题

协议它解决什么典型问题
SAML企业单点登录（IdP 签发断言，SP 信任） 签名没校验 / 只校验一部分 / XML 签名包装（XSW）
OAuth 2.0第三方授权（拿 token 访问资源） redirect_uri 校验不严 → 授权码送到攻击者
# OAuth：改 redirect_uri 看是否被接受
/authorize?client_id=x&redirect_uri=https://evil.example/cb&response_type=code
# 常见松法：前缀匹配（https://good.com.evil.com）、路径穿越、子域、@ 混淆

⑥ 条件竞争与"业务时序"

前面第 8 章讲过上传竞争。同一类问题在业务里更常见：先查后改、 先扣后加、先审后发。

场景怎么打看什么
优惠券只能用一次同一个券并发提交多份订单是否出现多份成功
余额提现并发发起提现总提现 > 余额
注册同名用户并发注册是否出现两个同名
限购一件并发下单订单数 > 1

工具箱里对应什么

host_bypass（Host 头）、smuggle（请求走私）、 cache_trick（缓存）、proto_pollution（原型链）、 saml_forge（SAML）、oauth_redirect（OAuth）、 race/upload_race（竞争）。

这些策略的分数普遍偏低（0.4~0.6），因为它们很难拿到"服务端亲口给的 flag"作为证据。 看到 0.5 分不要以为是失败，去看节点详情里的证据链。
